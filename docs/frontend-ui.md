# Frontend UI notes

Moved out of CLAUDE.md on 2026-11-20 (verbatim). Per-feature design decisions and gotchas for the client. Read the section for the page or component you're about to change.

## PWA auto-update

**PWA auto-update (2026-10-11):** `public/sw.js` only handles notification clicks and caches nothing, but a phone keeps an installed PWA alive in memory, so after a deploy it showed the old version until a manual refresh. Each build now gets an id (`vite.config.js`: `__BUILD_ID__` in the bundle plus a generated `dist/version.json`, served `no-store` via `vercel.json`); `utils/autoUpdate.js` refetches `/version.json` whenever the page becomes visible (and every 10 minutes) and reloads if the id differs. Production only.

## Install prompt

**Install prompt (2026-11-14, user's call):** signing up on a phone or tablet (not inside the installed app) marks `installPromptPending` (`utils/installPrompt.js`, from `RegisterPage`); `InstallPrompt.jsx` then shows once, in `ProximityDetector` after the location question is answered and the alerts opt-in is gone, with Show me how (`/guide?open=install`) or, when Chrome on Android offers `beforeinstallprompt`, Install; any answer clears it for good. Not on the guest welcome board (a guest hasn't decided to play yet), not for sign-ins. A second trigger, when an iPhone browser user tries to turn on alerts (impossible outside the installed app), is planned only if needed. Covered by `e2e/installPrompt.spec.js`.

## Installed app layout (phones)

**Installed app layout on phones (2026-11-26, user's design):** the installed PWA on a phone has no header; a tab bar at the bottom (`components/shared/BottomNav.jsx`, line icons in `NavIcons.jsx`) holds Dex, Map, Treasure, More and Profile (ZH 图鉴 · 地图 · 寻宝 · 更多 · 主页). History, the Guide, Achievements, the leaderboard (signed-in only) and Settings open from the new `/more` page (`pages/MorePage.jsx`; Settings opens the same window as the website profile's button), with Privacy and Log out (Log in for a guest) as a small row at the bottom; the More tab stays lit on all of those pages and on other players' profiles. In the app the profile has no buttons at all (user's call: it only shows what the player has done). **More fills exactly one screen on every phone** (user's call): its height is the screen minus the safe area, the top row (`--app-topbar-h`) and the tab bar; the tiles share it equally and are size containers, so the icon follows the tile height and the blurb drops to one line, then disappears, on short screens. Checked on seven phones from 320x568 to 430x932 in three languages by `e2e/pwaMoreFit.spec.js`. On top a slim row that scrolls away (`AppTopBar`) shows the wordmark (user's call: the page looked empty without it; a tap reloads) and, on the pages under a tab, a Back button on its left that goes back in the app's history, or to the tab's page when opened directly. Decided once at start in `utils/appMode.js` (`PWA_LAYOUT`: standalone, handheld, short screen side < 600, so iPads and installed desktop apps keep the website layout), which puts `pwa` on `<html>` and adds `viewport-fit=cover`: the page is padded by the safe areas, a strip of page colour sits under the status bar, `--navbar-h` becomes the top inset (sticky toolbars) and toasts/check-in rewards clear `--bottom-nav-h`. What the header held moved: theme and language into the Settings window (under More in the app) (on every screen, user's call), signed out (log in, sign up: no tab bar, no Settings) language and theme sit above the box with a note pointing to More › Settings (`components/auth/AuthPrefs.jsx`; user's call: the top row was too crowded, the wordmark stays centred), the level list is the profile's level badge, a guest's Login button sits on the profile. Explore leaves out its slogan title (e.g. "Collect Every Card in Prague") in the app and shows only a chosen area's name. `?pwa=1` previews the layout in an ordinary tab for the session (`?pwa=0` ends it). **Swiping between pages (2026-11-26, user's design):** in the app a sideways swipe on a tab's page goes to the next tab (left) or the one before (right) in the tab bar's order; on a page under a tab a swipe right goes back (`useSwipeTurn` in `PageTurn.jsx`). The page follows the finger (transform/opacity only), turns past 30% of the width or on a quick flick (slides out, the new page comes in from the finger's side: `state.turn = 'back'` gives the back turn to a PUSH), else springs back; past the first or last tab it gives only a little. Not taken over: a mostly vertical drag, the map (`.leaflet-container`, whose own drag stays), anything scrolling sideways, form fields, windows/sheets/the showcase, a pinch-zoomed page. Covered by `e2e/pwaSwipe.spec.js`. `#root` clips its sides (`overflow-x: clip`): a page turning in slides 28 px from the side, which made a long page wider than a phone for a moment, and the browser zoomed the view out, so the tab bar dropped and slid back on every switch to Explore, Treasure Hunt or Profile (user's report, 2026-11-26). Covered by `e2e/pwaLayout.spec.js`.

## Launch screen

**Launch screen (2026-11-12):** an installed PWA used to start on a white screen. `index.html` now carries a boot splash (`#boot-splash`: the emblem and the gold blackletter wordmark on navy, `/brand/splash-emblem.webp` and `/brand/splash-wordmark.webp`), painted with the HTML and faded out by `window.hideBootSplash` once the sign-in check is done (AuthContext), at most 8 s. iOS gets matching `apple-touch-startup-image` PNGs per device size in `public/brand/splash/`, and `manifest.json`'s `background_color` is the same navy (`#111428`) for Android's own splash. All of it is drawn by `node scripts/generateSplash.mjs` (client/); the device list there and the `<link>` tags in `index.html` must match. iOS only picks up new startup images after the app is removed and added to the home screen again.

## Explore entrance

**Explore entrance (2026-11-12, user's idea, every screen):** once per page load, the first time Explore shows its cards, the rows of cards in view drop into place like bricks in a diagonal wave from the top left. With the side column (`data-enter-mode="side"`) its blocks slide in from the left one after another; without it (`"stack"`: phones, upright tablets, narrow windows) the title, filters and count fade down in turn, and the whole thing is shorter and drops from less high (about 0.8 s, 36 px instead of 64 px), because an installed app plays it on every cold start (user's call: every time, not once a day) (`hooks/useExploreEntrance.js`, CSS at the end of `pixelart.css`). Guests and signed-in players alike; skipped under `prefers-reduced-motion`. State is on the DOM (`data-enter` on `.explore-page`, `data-enter-brick` and `--enter-delay` on cards), and only `translate` and `opacity` move, so the cards' own `transform` (hover, flip) and `useFitRows` are untouched. On `/explore` the boot splash now stays until the cards are there (the hook lets it go, after waiting up to 600 ms for the first covers), so the wall starts as the splash fades; on other pages AuthContext still hides it.

## Location consent (GDPR)

**Location consent (GDPR, 2026-10-22):** no code may ask the browser for a position before the user agrees. `utils/locationConsent.js` holds the decision (`localStorage.locationConsent`, `{ granted, version, at }`); `getCurrentPosition` opens `LocationConsentDialog` first when there's no consent (so only call it from a user action; background callers check `hasLocationConsent()`), and `useProximityDetection` only runs with consent. The dialog shows on first open, both answers look the same (no nudging), and the app works without location. `/privacy` (`PrivacyPage.jsx`, reachable without guest mode) is the art. 13 notice plus allow/withdraw; **raise `LOCATION_CONSENT_VERSION` whenever the dialog or the notice changes what it says about location**, so everyone is asked again. Signed-in users' decisions are saved as proof on `User.locationConsent` (`PUT /api/user/location-consent`, `LocationConsentSync`, newer decision wins). Server side, misses no longer store a position, and the treasure hunt's `trendRef` (the only stored position) is cleared when the hunt ends or consent is withdrawn (`LOCATION_CONSENT_VERSION` went to 2 on 2026-10-29 when that reference point stopped being hardcore-only); `npm run purge:hunt-positions` (server/) deletes old ones. The controller is the user as a private individual (no company); `PrivacyPage.jsx` gives only `CONTROLLER_EMAIL`, with no name yet (user's call, 2026-10-22). Art. 13(1)(a) also asks for the controller's identity, so remind the user to add a name before the public launch. Playwright's config pre-agrees via `storageState`; `e2e/locationConsent.spec.js` tests the dialog.

## Map itself

**Map itself (`MapView` with `vectorBase`):** our own vector street map (`utils/mapStyle.js`, a palette per theme, no point icons) on OpenFreeMap's public tiles through MapLibre (`MapVectorBase`, lazy, about 390 KB gzipped with its worker). OpenFreeMap is free and unmetered but promises nothing, so with no WebGL, a failed style or several failed tiles the map falls back to OSM's images. **Gotcha:** MapLibre's default build has its worker inline and it doesn't survive Vite, so `vite.config.js` aliases `maplibre-gl` to the CSP build and `MapVectorBase` calls `setWorkerUrl` with the CSP worker; the two must be from the same build or tiles die with "is not iterable". Don't paint OpenMapTiles' `park` layer: it holds protected areas and turns the historic centre green (city parks are `landcover` grass). `MapBoundaries` draws, under the markers, the city outline (ČÚZK's own, `utils/pragueCity.json`, written by `buildPragueAreas.mjs`), the district lines and the chosen quarter's line, and darkens what lies outside the area in play (solid shapes on a translucent pane, so overlaps don't get darker). A click on the map itself goes down a level (`MapBoundaries`): to the district there, then, inside the district in play, to the quarter, whose lines show once a district is chosen; markers don't bubble their clicks, and a click on the quarter already chosen or outside Prague does nothing. `MapAreaFocus` opens on the whole city (with Show all on Central Bohemia, `CENTRAL_BOHEMIA_BOUNDS`, and switching modes with nothing chosen goes to that mode's view; 2026-11-15, user's call) and fits a chosen area exactly (only that move may stop between zoom levels; `Markers` rounds the zoom). No zoom buttons: top left is the compass (`public/map/compass.webp`, magenta background keyed out), top right Go to My Location and View Whole City, bottom left a scale bar, bottom right the legend. `MapFrame`: heavy outer rule, a paper band with sparse ticks, a fine inner rule, a star tile on each corner, straight lines on purpose so it doesn't repeat the rarity cards' curling corners (user's calls: no block band, no column dividers). On the night map locked dots are white. Colouring dots by rarity was considered and dropped as too busy (user's call). **Show all is fenced to the Czech Republic (2026-11-15, user: the map can be dragged out but not past the border):** a hard box fence (`fenceOf` in `MapView.jsx`), and since its corners lie in the neighbouring countries, `MapAreaLimit` glides the view back whenever a move ends with its centre outside the border itself (`utils/czechBorder.json`, 446 points, from ČÚZK RÚIAN layer 19 by `node scripts/buildCzechBorder.mjs`); only the centre is held, so places on the border can still be viewed with some of the neighbour around them.

## Card showcase

**Card showcase (2026-10-12, `CardShowcase.jsx`):** a long press (touch, 450 ms, cancelled by >10 px of movement) or a right click (mouse; a double click until 2026-11-16) on a collected card (`LocationCard`, any page) opens it full screen: the same card scaled evenly to 92% of the screen height (or width), full-size cover instead of the thumbnail, the page dimmed like a spotlight and a glow in the rarity colour. ## Cover images

**Cover images (local-first):** Location covers load from `client/public/pixel-art/` before ever touching Cloudinary, to keep image traffic off Cloudinary's quota — Cloudinary stays fully wired up as the fallback/upload backend, just not the default read path. `utils/coverManifest.json` (generated by `npm run generate:covers`, see Commands) maps `slug -> filename`, since files are named `<slug>.<ext>` or `<slug>-v<timestamp>.<ext>` (the versioned form is a cache-buster used both by regenerated external pixel art and by the dev-mode cover-upload endpoint, which also patches this manifest directly — see `updateCoverManifest` in `locationController.js`). `utils/localCover.js`'s `getLocalCoverPath(slug, cloudUrl)` does the lookup. `LocationCard`, `LocationDetail`, `MapPage`'s `SidebarDetail`, and `RandomDrawPage` each try, in order: local manifest match → `location.coverImage` (Cloudinary) → emoji fallback (`getArt`), and each passes `location.coverImage` as the second argument. **Local wins only while it is not older than the Cloudinary upload (changed 2026-09-21):** `getLocalCoverPath` compares the local filename's `-v<ms timestamp>` with the Cloudinary URL's `/upload/v<unix seconds>/` version, and when Cloudinary is newer it returns `null` so the caller falls through to Cloudinary. This is what makes a cover edited through the app's Edit button (which only touches Cloudinary + the DB in production — see `uploadCoverImage`) show up immediately, without a re-sync. Before this, local unconditionally won whenever a manifest entry existed, so in-app edits on any card with a synced local file were silently hidden (found when a batch of ~70 newly synced covers was committed). A local file with no `-v<timestamp>` in its name can't be compared and still always wins. Running `node src/data/syncCovers.js --refresh` (server/) then `npm run generate:covers` (client/) is still the way to pull Cloudinary's current image down to a local file (plain `node src/data/syncCovers.js`, no flag, only fills in slugs with no local file at all), and it does save Cloudinary traffic, since a synced file is newer than the upload it copied. After manually dropping new art into `pixel-art/` outside the upload endpoint, name it `<slug>-v<Date.now()>.webp` (a newer timestamp than the card's Cloudinary version, or the older Cloudinary cover will win) and rerun `npm run generate:covers` to pick it up. Covered by `src/__tests__/localCover.test.js`.
  - **Card thumbnails (2026-09-25):** originals are 1024–2048px (~150KB avg) but a grid card shows them at ~180–300 CSS px, which made mobile Explore slow. `npm run generate:covers` also writes a 480px-wide copy of every mapped cover to `public/pixel-art/thumbs/<same filename>` (via `sharp`, a client devDependency; existing thumbs are reused, orphaned ones deleted). Thumbs are generated automatically on every path a cover can arrive by: `npm run build` (so also on Vercel) and `npm run dev` both run `generate:covers` first, a small plugin in `client/vite.config.js` reruns it when a cover is added to or removed from `pixel-art/` while the dev server is up, and the server's dev-mode upload endpoint and `syncCovers.js` write the thumb themselves via `server/src/utils/coverThumb.js` (its `THUMB_WIDTH` must match the client script's). Still **commit `thumbs/` alongside any new cover**, so the Vercel build only has to fill gaps. Because the build rewrites `coverManifest.json` from the files actually in the repo, a manifest entry for an uncommitted cover gets dropped on deploy instead of shipping a broken path. `LocationCard` loads `toThumbPath(localCover)` with `loading="lazy"`, falling back to the full-size local file if the thumb is missing (e.g. after a dev-mode upload before regenerating), and requests Cloudinary fallbacks through `toCloudThumbUrl` (`f_auto,q_auto,w_480`). Detail views (`LocationDetail`, `MapPage`, `RandomDrawPage`) still use full-size covers. `client/vercel.json` gives versioned `/pixel-art/*-v<timestamp>.*` files a 1-year `immutable` cache and other `/pixel-art/` files 1 day. Vercel's default for them was `max-age=0, must-revalidate`, so every visit revalidated every image.
