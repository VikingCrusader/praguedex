# History Timeline: frontend

Moved out of CLAUDE.md on 2026-11-20 (verbatim). Read before changing `/history` (`HistoryPage`, `HistoryBook`, `HistoryPaged`, `HistoryAxis`, `history.css`).

**History Timeline** (`pages/HistoryPage.jsx`, `components/history/`, `styles/history.css`): `/history` shows one event at a time, in the two views below.
  - **Two views, one event at a time (2026-11-08, user's calls).** `HistoryPage` picks by `BOOK_QUERY`: a 2K screen (2400x1200 and up) and Macs and iPads from 1024 px wide (`IS_APPLE` in `utils/fitPage.js`, from the user agent; iPadOS reports itself as a Mac) get `HistoryBook`; every other screen, phones included, gets `HistoryPaged.jsx`. Both have the `HistoryAxis` timeline. **`HistoryPaged`:** a normal scrolling page turned with the buttons, arrow keys or, on touch, by pulling on 90 px past the end. From 1024 px the text is on the left and images (stacked), landmarks and achievements on the right, the two the same height; the landmarks show whole, nine a page at most (whole rows: 8 at two or four to a row), and the right column may run past the text. Related achievements and reading are placed after measuring (`place` in `EventPage`): in the free space under the landmarks, else under a short text, else, if the columns can grow by up to `MAX_GROW`, in the shorter gap, else one compact panel across the bottom (user: no extra component if it can be avoided). Background cards open from related reading, under the columns. Narrow screens stack. On Macs and iPads the book view's images and captions are tightened to leave the landmarks room (`max-width: 2399px, max-height: 1199px` block at the end of `history.css`); a tap opens a cut-off caption (`is-open`), since hover doesn't exist on touch.
  - **Book view (from 2026-11-05):** `HistoryBook.jsx`: one event per screen, turned with the buttons or arrow keys, never by scrolling the page; only a panel with too much content scrolls inside itself. Both build on the pieces exported from `HistoryEventSection.jsx`. `?event=<slug>` opens an event; next/previous replace the history entry, in-text links push one. `HistoryAxis.jsx` is the timeline: a sliding band of eras (longer eras wider, click to jump) with the current era centred, and the events on a line that slides under a fixed gold frame, so the current one stays centred. Both bands can be dragged, with a flick carrying on (`useDragBand`, transforms written straight to the DOM); a click or a page turn glides them back. Background cards take no page in either view (`groupPages` in `utils/historyPages.js`): each hangs on the events listed for it in `server/src/data/backgroundHosts.js` (hand-picked 2026-11-12, sent as `attachedTo`; the first is its home, where an old link or position lands; only events that read badly without the card, at most 3 cards per event, checked by a test; a card with no entry hangs on the event before it, so **give a new background card an entry when it explains the event after it or is needed on several pages**) and opens in a floating window over the right column from the read-more panel (background cards, references, Wikipedia; beside a lone image, otherwise beside the landmarks), one button per card with its title; an in-text link to one opens it without turning the page. An old position or URL naming one shows its host page with the window open. The landmark panel pages instead of scrolling (`LandmarkPager`: renders all cards once, scales rows down to fit, splits into whole rows).
  - **Related achievements (2026-11-05):** `data/achievementHistoryEvents.js` (server) pairs achievements with events by hand, deliberately not by shared places. `GET /api/user/achievements` returns them as `historyEvents`; `HistoryPage` fetches that list once and attaches `relatedAchievements` to each event (`EventAchievements`, with progress for signed-in users, in the read-more panel and on phones under the landmarks), and `AchievementModal` links back with `/history?event=<slug>`. Add a pair when an era that an achievement belongs to is written (`the_ex` waits for the Velvet Divorce).
  - **Sticky-positioning gotcha:** `.guide-page` (shared by `GuidePage`, `TreasureHuntPage`, and `HistoryPage`) sets `overflow-y: auto` in `pixelart.css`. `#root` only has `min-height` (not `height`), so `.guide-page` never actually needs to scroll internally in practice — the real scrolling always happens at the window level — but the `overflow-y: auto` declaration alone still makes it a CSS "scroll container", which silently breaks `position: sticky` on any descendant (sticky computes against the nearest scroll container, and `.guide-page`'s own `scrollTop` never moves). `history.css` overrides it back to `overflow-y: visible`, scoped to `.history-page` only — don't remove that override, and don't add `position: sticky` inside `.guide-page` on another page without adding the same kind of scoped override.
  - Related landmarks render inside the shared `.location-grid` class from `pixelart.css` (so column widths/gaps match Explore's grid), but each grid item is a `.history-landmark-item` wrapper (flex column: `LocationCard`, then its relation caption right underneath) — not a bare card — see `HistoryEventSection`. An earlier version kept cards as direct, unwrapped grid children specifically to preserve CSS Grid's default `align-items: stretch` (uniform card height per row), with captions rendered in a wholly separate second grid below; replaced (2026-08) because captions needed to sit directly under their own card, not just visually approximated via matching column math. Cards in a row still get equal heights (2026-10-22, user request): each wrapper is a two-row subgrid (`grid-row: span 2; grid-template-rows: subgrid`, under `@supports`), so the card row stretches to the tallest card and the captions start on one line; the flex column is only the fallback. Rows are balanced and short rows centred (same day): each card spans two of six tracks (four below 722px container width), `landmarkStarts` in `HistoryEventSection.jsx` gives 4 → 2+2 and 7 → 3+2+2 on desktop, and the "See it for yourself" heading is centred too (user's preference). Phones (≤600px) keep both left-aligned, as before.
  - **Load performance (2026-09-25):** the payload holds every event, so four things keep it fast; don't remove them casually. (1) `GET /api/history?lang=<en|cz|zh>`: the client sends its language and the controller collapses every `{ en, cz, zh }` object to `{ [lang]: value || en }` (~1 MB → ~0.35 MB compressed), so switching language refetches. Without `lang` all languages come back. Landmarks carry only LocationCard's fields. (2) The controller caches the assembled payload in memory per language, checked on every request against the count plus newest `updatedAt` of `historyevents` and `locations`. A Mongoose `updateOne` sync (which bumps `updatedAt`) or a reseed shows up on the next request; a raw-driver write that doesn't touch `updatedAt` would not. (3) `.history-detail-panel` has `content-visibility: auto` (`visible` in `HistoryPaged`), and `LocationCard`'s label fit skips cards the browser isn't rendering (`checkVisibility`) and lets its ResizeObserver fit them later. (4) Event images are `loading="lazy"` with `width`/`height` from `src/utils/historyImageSizes.json`, generated by `scripts/generateHistoryImageSizes.mjs` (runs before `npm run dev`/`npm run build`, and on file changes in `public/history/` while dev is running), so lazy images don't shift the layout.
  - **Reading progress (2026-09-25):** `/history` reopens at the event the reader was last on (`activeSlug`). Every reader gets a `localStorage` copy (`historyProgress`, `utils/historyProgress.js`); signed-in users also get a server copy on `User.historyProgress` (`GET`/`PUT /api/user/history-progress`), and on load the newer of the two wins, so progress follows a user across devices. Server saves are debounced 2 s (3 s until 2026-11-04, shortened so a position held 2 s counts for Turning the Page) and flushed (fetch `keepalive`, `saveHistoryProgressOnExit` in `api.js`) when the page is hidden or the user navigates away. `HistoryPage` sets `history.scrollRestoration = 'manual'` while mounted, since the browser's own pixel-offset restore would land somewhere arbitrary. Nothing is saved until the restore has run, so the initial state never overwrites a saved position. **A return within the visit draws the book once, as it turns in (2026-11-13):** the position is kept in `pageCache` (`historyPos`), so the server is only asked on the first visit; the related achievements start from the cached `/achievements` payload (shared with the Achievements page and the profile); and a refetched payload that equals what is shown (`sameJSON`) is dropped. Before, the page turned in blank, then drew the whole book up to three times.
  - `unlocked` is force-set to `true` when a landmark is passed to `LocationCard` here — History isn't a discovery/gamification context (the event text already names the place), so Explore's "???" mystery treatment never applies on this page, regardless of the requester's real check-in state.
  - Clicking a landmark card opens the real `LocationDetail` as an overlay on top of the History page itself (`HistoryPage` owns `openLandmarkSlug` state and renders `<LocationDetail>` directly, same pattern `RandomDrawPage` uses) — not a navigation to `/explore`.
  - Each event's `<h2>` title doubles as its Wikipedia link (new tab, no underline, only a hover color shift) when `wikipediaUrl` is set — replaced an earlier standalone "Wikipedia" text link below the summary (2026-08).
