# History Timeline: data model and writing rules

Moved out of CLAUDE.md on 2026-11-20 (verbatim). Read before writing or editing any History Timeline event, background card or overview card. Era status lives in `docs/history-era-notes.md`, illustration rules in `docs/illustrations.md`.

## HistoryEvent model

- `HistoryEvent` — `slug`, `era` (key into `data/historyEras.js`), `startYear` (numeric sort/timeline anchor, negative = BCE, not localized — a bare number reads fine in any language), `title`/`hookLine`/`summary`/`year: { en, cz, zh }` (`year` is the localized display string, e.g. `"935 (traditional date)"` / `"935 (tradičně uváděný rok)"` / `"935年（传统纪年）"`), `tone` (`humorous`/`serious`, stored but not yet read by the frontend), `quotes: [{ text: {en,cz,zh}, attribution: {en,cz,zh} }]` (primary-source quotes, referenced from inside `summary` via a `"[[quote:N]]"` marker on its own paragraph — see **Primary-source quotes** below), `relatedLandmarks: [{ slug, relation: { en, cz, zh } }]`, `wikipediaUrl`, `images` (array of static paths, e.g. `['/history/prehistory.webp']`), `imageCaptions: [{en,cz,zh}]` (optional small caption rendered under each image, matched to `images` by array index — an entry can be left `{}` for an image that doesn't need one). `summary` text may also contain inline `"[[link:slug]]display text[[/link]]"` markers (see **In-text cross-reference links** below) and `"[[b]]emphasized text[[/b]]"` markers for plain bold emphasis (see **In-text emphasis** below).

## Backend

**History Timeline** (`models/HistoryEvent.js`, `data/historyEras.js`, `data/seedHistoryEvents.js`, `controllers/historyController.js`): a second, separate content type from Location — hand-curated historical events grouped into eight eras, browsable at `/history` on the frontend. `data/historyEras.js` is a static config (same reasoning as `RARITY_XP` in `rarityMap.js` — small, rarely-changing enum, not worth a DB collection) listing all eras with `key`, `order`, `themeClass`, `title: { en, cz, zh }`, `yearRange`, `tagline`, and `hasContent` (flip it manually once an era's events are seeded). As of 2026-08-23, `legends-origins`, `bohemian-duchy`, and `rise-of-a-kingdom` have real content; `kingdom-golden-age` and everything after are still placeholders. **Era 3/4 split (2026-08-23):** what used to be one era, `kingdom-golden-age` spanning 1199–1378, got split into two on the observation that "Bohemia's golden age" in actual historiography means Charles IV's reign specifically (1346–1378) — not the 148 years before it (Otakar II's rise-and-collapse, the Wenceslas II guardianship crisis, the 1306 Přemyslid extinction, John of Luxembourg's own reign as a rarely-in-Bohemia "wandering king" mortgaging crown lands rather than building anything lasting). `kingdom-golden-age` kept its key and now refers only to 1346–1378 (`hasContent` flipped back to `false` until real Charles IV events exist); the new era `rise-of-a-kingdom` covers 1199–1345 and inherited all ~32 previously-seeded events from the old single era (none of them post-date 1345). **`yearRange` corrected 2026-08-26 to 1199–1346:** the era's own content later grew to include John's 1346 death and Charles's 1346 King-of-the-Romans election, kept as `rise-of-a-kingdom`'s own closing bookend at the user's explicit direction rather than moved to `kingdom-golden-age` — the two eras now deliberately share 1346 as a boundary year, not by mistake. `GET /api/history` returns `{ eras, events }` in one payload — no list/detail split like `/api/locations`, since event copy is a few short hand-written sentences rather than a heavy lazily-generated description. Each event's `relatedLandmarks` stores bare Location slugs; the controller resolves them against the live `locations` collection in one batched query, enriches each with the full Location document (`-description` projection) plus a per-request `unlocked` flag computed the same way `getLocations` does it (via `CheckIn` lookup against `optionalAuth`'s `req.user`), and **silently drops any slug that doesn't resolve** rather than sending the client a dead link.

## Adding new history events (`data/seedHistoryEvents.js`)

- Every event needs `title`, `hookLine` (one-sentence hook), and `summary` (2–3 sentences) in all three languages.
- **Voice**: default to wry, deadpan comic history-writing in all three languages — short punchy sentences, concrete specific details kept rather than smoothed into abstraction, and a dry closing line that reframes the facts as a joke. Model paragraph (`vysehrad-revival-1070`, the 1075 Langensalza / 1077 "Gebhard" aside): *"两人较劲用了不同的招——一个靠打仗立功，一个靠改名讨好皇帝——看来'想方设法气对方'才是这家人真正代代相传的东西。"* That's the target register for pre-modern content generally, not just this one event. Exception: modern-era atrocity/mass-death content (e.g. Lidice) stays solemn — same format, drop the jokes, not a Lidice-only rule. **Broader 20th-century pullback (confirmed 2026-08-24):** once content reaches the eras `brief-independence` (1918–1938), `nazi-nightmare` (1938–1945), and `cold-war-sorrow` (1946–1992) — see `data/historyEras.js` — default to a more restrained, measured voice generally, not just for individual atrocity-tagged events within them. Dry irony and understatement can still land (e.g. an era tagline noting Czechoslovakia's allies "hand it over to appease the neighbor next door"), but drop the punchy joke-closer structure that defines the earlier-era default, especially for anything touching occupation, violence, or repression directly. The material carries more sustained weight than earlier eras; the wit shouldn't be the default assumption that then gets card-by-card overridden.
- **Dash frequency (confirmed 2026-08-25):** em-dashes (`—`) had crept into overuse across all three languages, and the density itself makes sentences feel long and hard to read — pull back the frequency in new History Timeline prose, EN/CZ/ZH alike. Prefer a plain comma, a period and a new sentence, a colon where the aside is doing real explanatory work, or parentheses for a genuine aside/qualifier. **Not a ban** — the user confirmed explicitly ("也不是完全不能用破折号，但是要在不得不用的时候才用"): treat it as a last resort, reached for only when none of those alternatives actually works, not as one option among several to pick freely. This is a general house-style tightening, not specific to one language (compare [[feedback_natural_sentence_style]], which flagged the same tic as a ZH-specific "AI tell" — that observation still stands, but the fix now applies everywhere).
- **Shorter paragraphs** (confirmed 2026-10-07, after the user split `two-kings-1438`'s opening paragraph twice and asked for clearer paragraphing from now on): in `summary`, give each idea or story step its own paragraph (the problem, the cause, the decision, the action) instead of packing several beats into one block. A paragraph of more than about 4–5 sentences, or one that changes topic partway, should usually be split. Use the same breaks in EN/CZ/ZH.
- **Avoid the "this timeline" self-reference** (confirmed 2026-08-30, user said it reads badly and explicitly dislikes it): don't write card copy that breaks the fourth wall to talk about "this timeline" as a narrating entity — "this timeline already covered...", "这条时间线已经讲过...", "tahle časová osa už..." — even though this exact device had been in near-constant use across the whole file before this date (roughly 70–80 occurrences at the time it was flagged). Prefer a [[link:slug]] cross-reference (see below) when the callback target has its own card, or just rephrase the callback to an in-story actor instead of the meta-narrator — e.g. "Charles's own court had already worn out the story it was so eager to spread" rather than "this timeline has already told the story Charles's own court was so eager to spread." This is confirmed as a going-forward default for all new/edited copy; the large stock of already-shipped cards using the old device was NOT swept retroactively as part of this fix — only ask about a full retroactive pass if the user raises it, don't assume it's wanted.
- **Vary the forward-hook closer** (confirmed 2026-08-25): a card that deliberately doesn't finish its own story (leaving the actual next event for its own card) needs some closing line gesturing at what's coming, but "接下来发生的事，是另一个故事了" ("What came next is its own story") had become a reflexive default across the Rise-of-a-Kingdom arc — used on `crowned-twice-1307`, `seven-kings-then-none-1306`, `thoroughly-incompetent-king-1307`, `the-fleeing-princess-1310`, and others in a row. Don't lean on this one stock phrase every time. Vary the construction: name what's coming without narrating it ("what he did with it is its own story"), end on an image or irony instead of a meta-statement about "the story," pose it as an open question, or just stop cold on the last concrete fact and trust the reader to feel the cliffhanger without a signposting sentence at all. The underlying job (close this card without spoiling the next one) stays the same; the sentence doing that job shouldn't read identically card after card.
- **Primary-source quotes** (`quotes: [{ text: {en,cz,zh}, attribution: {en,cz,zh} }]`, added 2026-08-24): when `summary` needs to quote a chronicle or historian directly (the Zbraslav Chronicle, Palacký, Henry of Heimburg, etc.), don't just embed the quote inline as quoted prose inside a regular paragraph — pull it into its own `quotes[]` entry and drop a `"[[quote:N]]"` marker on its own line (surrounded by blank lines like any other paragraph break) at the point in `summary` where it should appear. **Proactively suggest one, don't wait to be handed the quote text** — when researching an event and a genuine primary-source line or a notable historian's own verdict turns up (in a chronicle, in a WebSearch result, anywhere), pull it into this format on your own initiative, the same way background-card and territory-map opportunities already get flagged unprompted elsewhere in this doc. **This means actively searching for one, not just noticing if one happens to surface** (confirmed 2026-08-25): whenever the user hasn't supplied chronicle text themselves, spend a WebSearch pass or two specifically looking for a primary-source line before finishing the card — if a first search comes up empty, a second, differently-worded pass is worth trying before concluding there's nothing (a real case: the first search for Elizabeth's 1310 escape in `the-fleeing-princess-1310` missed the actual chronicle passage entirely; a second, differently-phrased search found it, and it turned out more accurate than the modern-secondary-source detail already drafted into the prose). If a proper search genuinely turns up nothing quotable, that's fine — don't force a weak or tangential quote in just to have one. `HistoryEventSection.jsx` swaps that marker for a distinct blockquote — bordered box, large decorative quotation marks, italic text, right-aligned "— Source" attribution — instead of a plain `<p>`. Every inline quote that existed in the Rise-of-a-Kingdom arc as of 2026-08-24 (the Palacký quote, the "divine vengeance" Zbraslav quote, Henry of Heimburg's famine account, the Continuator of Cosmas welcome-scene quote, the Zbraslav "pleased the Bohemian king" line) has since been retroactively converted to this format at the user's request — this is now the standing convention for all quotes, not just new ones. **Gotcha when converting an inline quote:** check whether the original prose continued in the same paragraph right after the closing quote mark (no blank line) — if so, the marker needs an explicit blank line inserted after it too, or the marker paragraph ends up with trailing text glued onto it and fails the `^\[\[quote:(\d+)\]\]$` match (rendering as a broken visible-marker plain paragraph instead of a blockquote). `node --check` won't catch this; only visually re-checking each `[[quote:N]]` occurrence's surrounding context will.
- **External video/film references** (`referenceMaps` — originally map-only, later reused for this — see "Content gotchas and lessons" below — confirmed 2026-09-02): whenever researching an event turns up a real film or documentary clip dramatizing it (a period film, a museum/documentary excerpt), don't just let it go unmentioned — proactively surface it via a `referenceMaps` entry (`label` = the year, `description` = a one-line note on what the clip shows, `url` = the link), the same unprompted-suggestion instinct already applied to primary-source quotes, background cards, and territory maps elsewhere in this doc. First used on `the-first-defenestration-1419` (a scene from the 1955 Czechoslovak film *Jan Žižka*, supplied by the user). **Extended 2026-10-08 to famous artworks** (user's explicit praise and request): a well-known painting of the scene (e.g. a Mucha *Slav Epic* canvas, a 19th-century history painting) gets the same treatment, with `label` = the year it was painted and `url` = a museum/foundation page. First used on `the-chalice-and-the-pope-1462` (Mucha's *The Hussite King Jiří of Poděbrady*, 1923). A one-line mention in the prose that the artist painted this very scene works well alongside it. This is a "when you happen to find one" convention, not a mandate to go WebSearching specifically for film adaptations the way the primary-source-quote rule mandates searching for chronicle lines — a good clip is a bonus if it surfaces naturally, not a required search pass.
- **Background-knowledge cards** (`cardType: 'background'`, default is `'event'`): a non-dated explainer aside slotted into the feed at a specific point, for context a reader needs right there but that isn't itself a dated happening — e.g. `bohemia-not-one-city-1101`, inserted between `duke-go-round-1092` and `battle-of-chlumec-1126` to explain that 11th–12th-century Bohemia had several rival power centers (Prague Castle, Vyšehrad, Olomouc/Brno/Znojmo in Moravia, plus assorted local strongholds) rather than one obvious capital, right before a battle whose whole premise depends on that. Renders with a distinct dashed-gold-border look and a collapsible "Background" tag instead of the normal year/title-as-wiki-link header (see `HistoryEventSection.jsx`, `history.css`), and — critically — takes no page of its own in the book view (see **History Timeline** under Frontend) even though it still needs a `startYear` to sort into the right place in the feed. **Proactively suggest one** whenever a piece of genuinely useful but likely-obscure context comes up that doesn't fit inside any single dated event — a European-history convention worth spelling out, a neighboring country's or the wider Empire's political backdrop, a term or institution the reader needs defined before the next few events make sense. Don't wait to be asked; flag the opportunity the way the illustration-prompt and territory-map offers already get flagged (see the reminders elsewhere in this doc). **A background card can optionally carry an `image`** (rule relaxed 2026-09-02, see `the-five-roses-1394`'s Rožmberk coat-of-arms image below — a reference graphic the user supplied directly, not an AI-generated narrative illustration; captioned with its source per the user's own instruction). **A background card still never gets a non-empty `relatedLandmarks`, hard rule, no exception carved out for this** — it's supplementary knowledge only, not tied to a specific place. Confirmed explicitly by the user 2026-08-22 after an illustration and three landmark links were added to a background card and had to be stripped back out; revisited 2026-09-02 specifically on the image half of that rule (the user asked to add a real coat-of-arms image to `the-five-roses-1394` and, when told it broke the standing "no image" rule, chose to relax that half rather than treat this as a one-off exception — so future background cards may use an image too, judged the same way an event card's image would be, while the landmark-link half of the original rule stands unchanged). If a background card's topic naturally connects to a real landmark, hold that link for later and attach it to an actual dated event instead — don't attach it here. **Before writing one, also check whether the subject is going to become a protagonist of its own later** rather than staying background forever — e.g. the Vítkovci family (Rožmberk branch), name-dropped starting in Era 3's `iron-and-golden-king-1266` (Otakar founding `zlata-koruna`/`ceske-budejovice` to counterbalance them, confiscating `jindrichuv-hradec` from them) but deliberately *not* given a background card there (decided 2026-08-22): the Rožmberks become one of the most important noble families in later Bohemian history (Český Krumlov, active into the Hussite/Renaissance/Baroque eras, extinct 1611) and will very likely anchor their own dated event(s) later, where a proper introduction lands with more weight than a background aside now. A passing mention with no card is fine when this is true; don't spend a background card explaining someone who's about to get their own spotlight. **Update 2026-08-23: a short introductory background card now exists — `who-are-the-vitkovci-1276`**, inserted right after `enemies-on-every-side-1276`. Deliberately light: Vítek of Prčice's origins as a Přemyslid court official (cup-bearer 1165, seneschal 1169–75) turned South Bohemia/Austria-border landholder, his sons' split into the "Five Roses" branches (Krumlov, Rožmberk, Hradec, Landštejn, Stráž), and the general loyal-official-vs-rival tension — no mention of Záviš's later marriage to the widowed Kunigunda, his 1290 execution, or the Rožmberk branch's own later peak. **The deeper/fuller version is still deferred, standing reminder unchanged:** proactively flag it when the Rožmberk family specifically becomes a genuine protagonist of their own (Hussite-era Oldřich II in Era 5, first name-dropped in passing in `the-castle-nobody-came-to-save-1428` (Bechyně's lord had fallen out with him, so no relief came; Bechyně was a Lefl-of-Lažany castle, not a Rožmberk one), user said 2026-09-26 to wait for his proper entrance; **written 2026-09-29 as `who-was-oldrich-of-rozmberk-1434`, placed between `the-new-town-falls-1434` and `lipany-1434` (moved there 2026-10-07; the old timing note below is kept for context)** — originally: **timing confirmed 2026-09-29: write it at Lipany (1434)**, inserted just before Oldřich's own entrance with the lords' league, since through 1432 he is still only a one-line side figure. `the-five-roses-1394` already covers the five branches and Rožmberk absorbing Krumlov, so the new card should center on Oldřich II himself (Lipany, leadership of the Catholic party, Sigismund's chief ally, his forged imperial charters exposed only in the 19th century), with `trebon` as his seat; Vilém/Petr Vok and Český Krumlov later still) — the user asked to be told, not to have to ask again. **When that fuller card gets written, explicitly callback to where this thread started** — this short 1276 introduction, Záviš of Falkenstein's revolt, the Zlatá Koruna/České Budějovice foundations built specifically to contain this family, and the Jindřichův Hradec confiscation — don't just reintroduce the family cold; tie the payoff back to the setup already on the record.
- **Era-overview cards** (`cardType: 'overview'`, added 2026-10-01): one per era, kept in `data/historyOverviews.js` (appended to `historyEvents` in `seedHistoryEvents.js`), slug `era-guide-<era-key>`, rendered by `HistoryOverviewCard.jsx` **in place of the era banner** (`HistoryEraDivider` is skipped for an era that opens with one). The card shows the era's title, years and tagline (from `historyEras.js`), then the card's own `title` as a subtitle, then `summary`: **one single humorous paragraph**, concrete (real people, real details) but not spoiling the era's biggest outcomes. **Settled after two rejected designs the same day** (the user found a multi-section version with cast/key moments/questions/reading time too busy, and before that a prose-plus-landmarks version too similar to event cards): keep it plain. No `hookLine`, no extra sections, no images, no `relatedLandmarks`, and gold only on the era title/years. `historyController` sorts events by era order, then overview first, then `startYear`. Since the seed is `$setOnInsert`, sync an edited overview by deleting and re-creating its doc. **Since 2026-11-14 (user's call) the overview cards are not shown:** they take no page (`groupPages`; a link or reading position naming one lands on the era's first page via `redirect`), and an era opens instead with `EraIntro` on its first event's page: chapter number, title, years and one plain line on what the era covers, from `client/src/utils/historyEraLines.js` (the same lines as the Guide's History window); on phones (≤600 px) the plain line is left out and the title, then the subtitle with the years, are each fitted to one line (`useFitHead` in `EraIntro.jsx`; a subtitle that won't fit at 14 px puts the years on a line of their own), 2026-11-14, user's call). **When a new era gets its first content, check its line there** (every era already has one); the overview docs stay in the DB.
- `era` must match a `key` in `data/historyEras.js`. `startYear` is the numeric sort/timeline-position anchor (negative = BCE) — for legendary/undated content, anchor it to the era's own conventional/narrative dating rather than a stricter archaeological date if the two diverge, so the timeline still reads in the intended story order (see the comment on `founding-of-vysehrad` for the actual case this came up).
- `relatedLandmarks` slugs must already exist in the `Location` collection — an unresolved slug is silently dropped by the controller, not an error you'll see. **Query the live DB, not just `seedLocations.js`** — a meaningful number of real, correctly-content-filled Locations exist only in the database (user-submitted through the app's own add-location flow, or added by an earlier script/session) and never made it into the seed file at all (`st-georges-basilica`, `namesti-miru`, `basilika-sv-petra-pavla`, and several `*-<random-digits>` user-submitted slugs among them as of 2026-08) — grepping the source file alone will produce false negatives. When searching by name, watch for Czech diacritics that look similar but aren't the same character (e.g. `í` vs `ě` in "Děvín" — a regex written for the wrong one silently returns nothing, not an error).
- **Known caveat, `prague-castle`/`st-vitus-cathedral` FIXED 2026-08-26:** these two Location slugs used to have swapped names (slug `prague-castle` held the genuine St. Vitus Cathedral content, slug `st-vitus-cathedral` held the genuine Archbishop's Palace content) — not a content bug, a slug-naming bug, discovered while wiring up `dawn-over-prague-1344`'s landmarks. Fixed by renaming both docs to their correct slugs (`st-vitus-cathedral` → the cathedral, `archbishops-palace` → the palace, freeing `prague-castle` entirely — a genuine "whole complex" card, if one ever gets written, needs fresh content, not this reclaimed slug) and updating every downstream reference: the 4 `relatedLandmarks` entries pointing at the old `prague-castle` slug across `seedHistoryEvents.js` (`wenceslas-life-and-reign`, `prague-bishopric-973`, `bretislav-succession-law-1055`, `vratislaus-ii-first-crown-1085`), the `castle_conqueror` achievement check in `gamification.js`, and the local cover image filenames in `client/public/pixel-art/` (regenerate `coverManifest.json` after any similar rename, don't hand-edit it). The Archbishop's Palace doc is DB-only, never made it into `seedLocations.js` — same "DB may hold docs the seed file doesn't" gotcha noted elsewhere in this file. **`vysehrad` is still mismatched** (named "Leopold Gate") and remains unfixed — still avoid linking to that one until it gets the same treatment.
- **Don't assume the DB matches what you seeded, even minutes later.** Twice in one session (2026-08-16), Location docs drifted from their just-seeded `rarity`/`labels`/`coordinates` shortly after creation, and a legitimate location once existed twice under two different slugs for the same physical place (`bazilika-sv-ludmily` vs. the pre-existing `namesti-miru`, the latter carrying a garbled, wrong-voice AI-generated description with stray pre-schema fields like `category`/`difficulty`/`isPreset`) — root cause undetermined in both cases. Before publishing new content that links to or duplicates a landmark, query the live doc directly (`Location.findOne`) rather than trusting the seed file or your own last edit.
- Chinese text follows the same rule as Location descriptions: no parenthetical foreign-language name glosses (e.g. no `莉布谢（Libuše）`) — just the Chinese name. A genuine content aside (not a name translation) is fine to keep in parentheses.
- **Title translation across languages doesn't need to be literal — different languages are allowed their own idiomatic phrasing (e.g. `the-crown-he-didnt-win-1254`'s ZH title is a Chinese meme riff with no direct EN/CZ equivalent) — but if an edit to one language's title changes its meaning significantly, the other two languages' titles must be updated to match that new meaning, not left pointing at the old one.** Confirmed explicitly by the user 2026-08-22 after `peace-with-cousin-bela-1254`'s ZH title was changed from a direct translation of the EN/CZ ("与堂兄的和解") to a differently-framed one ("与匈牙利六年的和平") and the user asked for EN/CZ to be brought in line ("Six Years of Peace With Hungary" / "Šest let míru s Uhrami") rather than left as the old framing.
- `image` is optional — a static file dropped into `client/public/history/` and referenced by its `/history/<file>.webp` path; renders as a banner between the summary and the Wikipedia link when present. A small caption line under a specific image is optional too (`imageCaptions[i]`, added 2026-08-30, matched by index to `images[i]`) — leave that index's entry as `{}` for an image that doesn't need one; not every image needs a caption. **`imageCaptions[i]` should not just restate the plaque caption baked into the artwork itself** (confirmed 2026-09-02) — the illustration prompt's own bold-serif plaque text already carries the punchy/thematic line; `imageCaptions[i]` should instead plainly describe what's actually happening in the scene (who, what moment, when), in plain narrative language, so the two captions do different jobs instead of echoing each other.
- **In-text cross-reference links** (`"[[link:slug]]display text[[/link]]"`, confirmed 2026-08-30): when `summary` prose needs to point at another event's own section — something the reader already met earlier, or a term/institution defined in its own background card — wrap the actual named phrase (already written per-language, not a separate label) in this marker instead of just writing an unlinked callback like "as this timeline already covered." `HistoryEventSection.jsx`'s `renderInlineLinks` turns it into an underlined, clickable inline span that opens that other event. **This explicitly replaces the old habit of just restating "正是这条时间线先前讲过的那样" (or its EN/CZ equivalents) as inert prose** — reach for the link instead whenever the referenced content already exists as its own event or background card in this file. The surrounding sentence can still keep the "already covered" framing for orientation; the linked span is the actual named thing, not a generic pointer word like "here." Distinct from `[[quote:N]]` — that one replaces a whole paragraph with a blockquote; this one sits inline mid-sentence and wraps text that's already there. **Keep the wrapped span short — a name or a short phrase, not a whole clause/sentence** (confirmed 2026-08-31, after `the-last-king-of-arles-1365` shipped with two links each wrapping a full clause, rendering as a multi-line underline that the user flagged as visually too long). A proper noun (`Anna of Świdnica`, `Arnošt of Pardubice`) is the ideal case; when linking to a past event by its content rather than a name, compress to a short noun phrase (e.g. "his own imperial coronation," "卜尼法斯八世倒台") rather than linking the whole sentence that describes it — rephrase the surrounding sentence if needed to make a short phrase the natural anchor. This wasn't swept retroactively across already-shipped cards with longer link spans (e.g. `italy-still-couldnt-forget-him-1350`) — only fix one if the user raises it.
- **In-text emphasis** (`"[[b]]emphasized text[[/b]]"`, confirmed 2026-09-02): same mechanism as the cross-reference link above (`HistoryEventSection.jsx`'s inline-markup parser handles both `[[link:slug]]...[[/link]]` and `[[b]]...[[/b]]` in one regex pass), but for plain emphasis rather than navigation — renders as `<strong>`, no click behavior. Unlike the link marker's "keep it short" rule, this one is meant to wrap a full load-bearing sentence, not just a name or short phrase — the point is making a summary paragraph's single most important claim visually stand out (e.g. a card's central thesis, a figure's core position stated outright) against the surrounding narrative prose, not highlighting individual words. First used in `who-is-jan-hus-1412`, bolding the sentence stating Hus's own core positions (opposition to Church corruption, simony, and indulgences; Christ alone as the Church's true head). **Proactively reach for this going forward** whenever a summary paragraph states this kind of load-bearing claim outright, the same way the link marker and quote blocks already get used proactively elsewhere in this file — don't wait to be asked each time.
- **`hookLine` never gets `[[link:slug]]` or `[[b]]` markers** (confirmed 2026-09-20, after a rendering bug shipped): `HistoryEventSection.jsx` renders `hookLine` as a plain string (`{convert(event.hookLine[lang] || event.hookLine.en)}`) — only `summary` paragraphs go through `renderInlineLinks`, the function that actually parses `[[link:...]]`/`[[b]]` markup into clickable spans/`<strong>`. A marker placed in `hookLine` renders as literal, broken-looking bracket text on the card instead of a link, since nothing strips or interprets it there. This bug had been shipping silently for a while (found across ~24 events spanning `legends-origins` through `kingdom-golden-age`, including some added during the 2026-09-19/20 `rise-of-a-kingdom`/`kingdom-golden-age` retrofit pass) before the user caught it from a live screenshot and it was swept and fixed project-wide in one pass. If a `hookLine` needs to reference something covered elsewhere, just name it in plain prose — no marker, since there's nowhere for it to render into.
- After writing new entries, run `node src/data/seedHistoryEvents.js` (from `server/`) to upsert them — just run it once content is done, no need to ask first. It's `$setOnInsert`-based like `seedLocations.js`, so **editing an already-seeded event's fields in the source file does not update the live DB** on a re-run — sync a live edit manually (e.g. `HistoryEvent.updateOne({ slug }, { $set: { ... } })`) or delete-and-reseed. **`seedHistoryEvents.js`'s own upsert loop is guarded** (fixed 2026-09-20, same pattern as `seedLocations.js`): it only fires via `if (import.meta.url === pathToFileURL(process.argv[1]).href)`, so `import { historyEvents } from './seedHistoryEvents.js'` in a one-off sync script is now side-effect-free and won't race a manual sync's own DB connection — see [[feedback_db_sync_write_durability]].

## Content gotchas and lessons

- **Vratislav vs Vladislav** — two different men a century apart: Vratislav II (r. 1061–92, first king 1085) vs Vladislaus II (r. 1140–73, second "borrowed crown" 1158). Established ZH: **弗拉季斯拉夫** = Vratislav, **弗拉迪斯拉夫** = Vladislav (季 vs 迪), checked against zh.wikipedia. Don't let a casually-typed draft suggestion "fix" this. No Bohemian Vratislav was ever crowned king except Vratislav II (`romansky-most-vysehrad` once said "Vratislav I"; fixed).
- **Verify large edits**: one large Edit silently turned straight quotes into curly quotes across a whole block (caught only by `node --check`). Re-run `node --check` after *every* large edit to `seedHistoryEvents.js`, not just before the DB sync.
- **Direct-DB sync writes**: a `troskovice` sync reported `modifiedCount: 1` and read back fine, then silently reverted (likely racing the un-guarded `seedLocations.js` upsert on import plus non-majority write concern). Fixed by guarding both seed scripts' upsert loops behind an `import.meta.url` entry-point check and by using `{ writeConcern: { w: 'majority', j: true } }`. For anything that matters, re-verify from a separate connection after a delay before saying it's live ([[feedback_db_sync_write_durability]]).
- **Live-DB drift** (standing gotcha): `hrad-trosky` is live as `legend`/100 XP while the seed says `epic`/50 (the rarity no longer matters: it is an expedition card). Unreconciled, root cause unknown — only `description` was synced.
- **`referenceMaps` reuse**: its UI label was genericized to "More on this:" / "延伸资料：" / "Více k tomuto tématu:" (`history.referenceMapsLabel`), which also changed the 5 map-only cards. First non-map use: the 1955 film *Jan Žižka* clip on `the-first-defenestration-1419`.
- **Background-card feature** touches `HistoryEventSection.jsx`, `HistoryBook.jsx`, `HistoryPaged.jsx`, `HistoryPage.jsx`, `history.css` and i18n keys `history.backgroundLabel`/`collapseCard`/`expandCard`; verify frontend changes with a full `vite build`, not just `node --check`.
- **`[[link:…]]` and `[[b]]` don't nest**: `INLINE_MARKUP_RE` in `utils/historyMarkup.jsx` matches them in one flat pass, so a link inside a `[[b]]…[[/b]]` span renders as literal bracket text. Keep links outside bold sentences (caught before shipping on `undefeated-until-the-plague-1424`).
- **Inline `[[link:…]]` renders as `<span role="button" tabIndex={0}>`, not `<button>`** (a `<button>` is an atomic box and won't wrap mid-phrase). Link color: default `var(--text-primary)`, gold only on `:hover`; the underline marks it as a link.
